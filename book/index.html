Front matter

Inference Engineering, measured on one laptop

A short book about why language models answer at the speed they do, and how to make them faster. Every number in it was measured on a single laptop, and every experiment can be re-run in a few minutes.

Who this is for

Someone who can run a Python script and wants to understand inference from the ground up: not a catalogue of techniques, but the small number of physical facts that all the techniques are built on. No prior knowledge of GPUs or machine-learning systems is assumed. Readers who know the field will recognise the material; the point here is to measure it rather than recite it.

How this book works

Each chapter teaches one idea and attaches an experiment. The experiments follow a fixed protocol: predict the result and write it down, run the script, then interpret the gap between prediction and measurement. The gap is where the learning is. A chapter is finished when the reader can explain its idea to someone else without the book.

Later chapters are shown as outlines so the shape of the whole subject is visible from the start. They fill in as the experiments are done.

Part I · Foundations · Chapter 1

The map

"Inference engineering" names a large field, but it has a simple shape: eight topics in three layers, each layer resting on the one below.

Layer 1 is about one question: what physically happens when a model produces a token, and how do we measure it without fooling ourselves. Layer 2 takes the three ways of making a single request faster. Layer 3 is about sharing a machine among many requests, where the arithmetic changes.

Much of the recent excitement in the field, including the DFlash paper that this book uses as a worked example in Chapter 11, lives in one box of Layer 2. Part I exists because that box cannot be understood, or its claims checked, without the layer underneath it.

Chapter 2

How a model makes a token

To write one word, the chip reads the entire book.

A language model's weights are a very large collection of numbers. Qwen3-4B holds about four billion of them. Stored in bf16, two bytes each, that is an 8 GB book. To produce one token, the chip must read every page of that book, do a little arithmetic with each page, and write down a single word. For the next token it reads the whole book again.

The chip reads memory at a fixed speed. On the reference machine that speed is about 441 GB/s (Chapter 3 shows how it is measured). Reading 8 GB therefore takes about 18 milliseconds, and in those 18 milliseconds exactly one token appears. The arithmetic the chip performs with those weights takes far less time than the reading. The GPU is mostly idle, waiting on memory.

The one idea

Decoding is memory-bound. The limit is how fast bytes move from memory to the chip, not how fast the chip can compute.

Two things almost everyone gets wrong at first

The weights are not being calculated. They were calculated once, during training, on thousands of GPUs. At inference time they are frozen numbers on disk, read but never changed. The only numbers computed on the laptop are the activations: temporary values that flow through the layers for this one input, used once and discarded. A book is written once and read many times. Inference is reading.

The model is not answering a question. It knows how to do exactly one thing: given some text, guess the next token. An answer is produced by asking that one question over and over. The prompt is read in one pass, the model guesses the token that comes after it, that guess is appended, and the model is asked again. Two hundred rounds make a two-hundred-token answer, and each round is one full read of the book.

What the model actually outputs

A model never outputs a word. It outputs a score for every token it knows. Qwen3's vocabulary has 151,936 entries: whole words, word pieces, punctuation, code symbols. After reading "Explain why the sky is blue." the model returns 151,936 numbers, one per entry, called logits. A high logit means "this is likely to come next". On the reference machine the five highest after that prompt were:

  20.88  ' The'
  18.25  ' \n\n'
  18.25  ' ('
  18.12  ' Also'
  17.38  ' '

Turning logits into a choice takes one of two steps. Argmax picks the highest, which is greedy decoding, the behaviour at temperature 0; the same prompt then always gives the same answer. Or softmax converts the logits into probabilities that sum to one and a token is sampled from them, with temperature controlling how much weight the runners-up get. Chapter 10 depends on this distinction: a speculative decoder is only correct if it reproduces the same distribution, not merely the same argmax.

Producing the logits is the model's last step, a multiplication by a matrix with one row per vocabulary entry: 151,936 × 2,560 numbers, about 0.78 GB in bf16, or a tenth of the book. It is called the lm_head, and it is read once per token like everything else.

One detail about prompts

Fed raw text, the model continues it as if writing an article. A chat command such as mlx_lm.generate first wraps the prompt in a chat template, roughly <|user|> Explain why the sky is blue. <|assistant|>, so that "the next token after the prompt" is the first word of a reply. Same mechanism, different framing. The model never knows it is answering a question; it only knows what text usually comes next. It also means the prompt the model sees is longer than the text typed: eight raw tokens became sixteen with the template on the reference machine.

Why this one idea predicts the next layer

If decoding is memory-bound there are only three ways to make it faster, and they are the three topics of Part II:

  • Make the book smaller. Store the weights in fewer bytes. That is quantization (Chapter 9). The 4-bit Qwen3-4B is a 2.3 GB book instead of 8 GB.
  • Write several words per read. If one pass over the weights could produce many tokens instead of one, each token would cost a fraction of a read. That is speculative decoding (Chapter 10), and DFlash's contribution is a drafter that produces up to 16 tokens per read (Chapter 11).
  • Waste less while reading. Make the read itself run at full speed and remove delays around it. That is the world of kernels (Chapter 12).
Build it. tiny-llm Week 1, chapters 1.5 "Load the Model" to 1.7 "Sampling", implements this loop from array operations: load the weights, run the forward pass, pick a token, append, repeat.
Chapter 2 in three sentences
  • The weights are fixed; the model reads all of them once per token.
  • Each read yields one guess, a vector of 151,936 logits; the answer is the guesses laid end to end.
  • Because reading dominates, speed comes from smaller books, more words per read, or less waste per read.

Chapter 3

Memory bandwidth

The spec sheet gives a number. The machine gives a different one. Use the machine's.

Where the spec number comes from

Bandwidth is how many bytes per second can flow between the memory chips and the processor. It is a product of two things. The bus width is how many wires carry data at once, like lanes on a highway. The transfer rate is how many transfers each wire makes per second.

ChipBus widthRateBandwidthvs. reference
Apple M4 Pro256-bit8533 MT/s273 GB/s0.5×
Apple M4 Max (reference)512-bit8533 MT/s546 GB/s1×
NVIDIA H100 (data-centre GPU)5120-bit HBM3~5.2 Gbps~3,350 GB/s~6×

A data-centre GPU reads the book about six times faster than the reference laptop. That one fact explains most of the gap between tokens-per-second figures in papers and figures measured at home. It is also why this book compares ratios and fractions of a ceiling rather than raw speeds across machines.

Measuring it

Spec numbers are peaks that no real program reaches. Memory cells need refresh cycles, the bus switches between reading and writing, and the processor does not always have the next request ready. The achievable number is found by creating a large array, making the GPU read all of it once with a sum, and dividing bytes by seconds. Script 01 in Appendix B does this for three sizes:

0.2 GB read in   1.05 ms ->   190 GB/s
2.0 GB read in   4.27 ms ->   468 GB/s
8.0 GB read in  18.15 ms ->   441 GB/s

The large reads give 441 to 469 GB/s, 81 to 86% of the spec, which is a normal fraction for this class of hardware. The small read gives much less, and that difference is the chapter's second lesson.

Fixed overhead

Every time the CPU asks the GPU to do something, there is a fixed cost before any bytes move: packaging the request, handing it over, starting the small program. On the reference machine that cost is roughly half a millisecond. A 2 GB read should take 4.3 ms, so the half millisecond is barely visible. A 0.2 GB read should take 0.43 ms, so the same half millisecond more than doubles the job and the apparent bandwidth falls by more than half.

Rule to keep

Small jobs are dominated by fixed overhead. Big jobs are dominated by bandwidth. This sentence explains why a quantized model never gets the full speedup its byte count promises (Chapter 4), why prefill on a short prompt cannot be measured meaningfully (Chapter 5), and, later, why speculative decoders prefer to verify many tokens at once (Chapter 7).

Exercise 3.1 · measure your own bandwidth
  1. Predict how long a 2 GB read takes at your chip's spec bandwidth.
  2. Run experiments/verify/01_bandwidth.py and compare. Expect 75 to 90% of spec on a healthy machine.
  3. Note how the 0.2 GB result falls short and estimate the fixed overhead in milliseconds from it.
Chapter 3 in three sentences
  • Bandwidth is bus width times transfer rate; the reference machine's spec is 546 GB/s and it delivers about 441 to 469 in practice.
  • Measure it on the machine; never plug in the spec sheet.
  • Every GPU operation carries a fixed cost, which dominates small jobs and vanishes in large ones.

Chapter 4

The roofline

A model's speed limit can be computed before the model is ever run.

Two ingredients, both already in hand. The book is 8.04 GB for bf16 Qwen3-4B and 2.26 GB for the 4-bit version. The reading speed is about 441 GB/s. Divide, and the result is the shortest possible time for one token, and therefore the highest possible tokens per second. Engineers call this limit the roofline, because on a plot of performance it is a ceiling nothing can pass.

ModelBook sizeFastest readCeiling
Qwen3-4B bf168.04 GB18.2 ms55 tok/s
Qwen3-4B 4-bit2.26 GB5.1 ms196 tok/s

The measurement

Script 02 runs the standard command, mlx_lm.generate, with greedy decoding and 200 new tokens, and reads its "Generation" line. On the reference machine, on AC power with nothing else running:

ModelCeilingMeasuredFractionPeak memory
Qwen3-4B bf165555.7 tok/s~100%8.11 GB
Qwen3-4B 4-bit196162.9 tok/s83%2.37 GB

Reading the two bars

bf16 sits on the ceiling. The weights take 18.2 ms to read and the measured step takes 18.0 ms per token (1000 ÷ 55.7). Within measurement error, the software is doing the minimum work physics allows. Nothing in Layer 2 can make this model faster except shrinking the book or getting more than one token per read.

4-bit is 17% short, and the shortfall is fixed overhead. The 4-bit book is 3.56 times smaller, but decoding is only 2.9 times faster (162.9 ÷ 55.7). Each 4-bit step takes 6.1 ms against a 5.1 ms read: about one millisecond of per-step cost that was also present in the bf16 step but hidden in a job three times larger. This is a general law. Quantization delivers less than the byte ratio, and the smaller the model, the less of the ratio it delivers. Chapter 12 is about recovering that millisecond.

What a reader can now do

Given any model's size in bytes and any machine's measured bandwidth, state its decode speed limit in one division, and say how far a measured number is from it. Every speedup claim in Part II is a claim about this fraction.

  2. Predict the fraction of the ceiling each will reach.
  3. Run experiments/verify/02_generate_cli.py and fill in a table like the one above. Record power source and background load beside it (Chapter 5 explains why).
Chapter 4 in three sentences
  • Ceiling = measured bandwidth ÷ bytes of weights.
  • On the reference machine bf16 decoding is at the ceiling and 4-bit is at 83% of its own.
  • Quantization's speedup is always less than its byte ratio because fixed overhead does not shrink with the model.

Chapter 5

Profiling a token

You cannot improve what you cannot locate.

Chapter 4 showed where a model stands against its ceiling. When it falls short, the next skill is profiling: splitting one token's time into parts and timing each. The first step is to list what has to happen.

Timing the forward pass alone

Script 04 loads the model, prefills the prompt so the cache is realistic, then times the bare call model(x, cache=cache) for one token: no sampling, no text, no generation loop. It does so twice, as a 20-step burst and as 200 sustained steps, because short bursts can mislead (see the case note below).

Qwen3-4B-bf16  burst(20)  18.8 ms | sustained(200)  19.0 ms
Qwen3-4B-4bit  burst(20)   7.3 ms | sustained(200)   7.1 ms

Against a pure read of 18.2 ms, the bf16 forward pass takes 18.8: the kernels inside the model lose about 0.6 ms, 3%. The 4-bit forward pass takes 7.1 ms against a 5.1 ms read, which is the per-step overhead from Chapter 4 seen from inside.

Timing what surrounds it

Script 05 times step 4 by itself, the argmax over 151,936 logits. Script 06 runs a real decode loop in which each step's input is the previous step's chosen token, which forces a CPU-to-GPU round trip (.item()) every step, and records every step's time.

argmax alone: 0.25 ms

Qwen3-4B-bf16, dependent loop, 200 steps
   steps   0- 19:  18.8 ms      steps 100-119:  18.9 ms
   steps  20- 39:  18.8 ms      steps 120-139:  18.8 ms
   steps  40- 59:  18.8 ms      steps 140-159:  18.8 ms
   steps  60- 79:  18.7 ms      steps 160-179:  18.8 ms
   steps  80- 99:  18.7 ms      steps 180-199:  18.8 ms
   mean  18.8 ms ->  53.2 tok/s

Qwen3-4B-4bit, dependent loop, 200 steps
   mean   7.1 ms -> 141.0 tok/s

Picking the token costs a quarter of a millisecond. The round trip costs nothing measurable: the dependent loop (18.8 ms) is indistinguishable from the bare forward pass (18.8 to 19.0). The per-step times are flat to within 1% across all 200 steps, so nothing degrades as the KV cache grows from 8 to 208 entries. The copper box of Figure 5.1 is nearly empty on this machine.

Case note · the day the laptop ran at half speed

On the first two days of these experiments the same generate command reported 26.6 tok/s for bf16 and 85 tok/s for 4-bit: about 45% of the ceilings. Short 20-step bursts of the forward pass were fast (19.9 ms) while longer runs were slow (36 to 41 ms), which looked like a thermal or cache-growth effect inside the model. Two days later, with the machine on AC power and idle, everything measured at the roofline and burst and sustained agreed to 0.1 ms. The slowdown was environmental and it was never identified; the candidates are battery power, Low Power Mode and heavy background processes. The episode is kept here because it is the commonest way profiling goes wrong: a gap that lives in the machine's state gets hunted for inside the code.

Measurement rules from this chapter

  • Re-run the baseline in the same session. A comparison between a fresh number and a two-day-old one is a comparison between two machine states.
  • Record the environment. Power source, Low Power Mode, and the top background processes belong beside every number, as the model and prompt do. Script 00 prints them.
  • Run as long as the real workload. Time 200 steps, not 20. On a healthy machine they agree; when they disagree, the disagreement is the finding.
  • Ask whether the number is possible. A step that times slower than a loop doing strictly more work means the instrument is broken, not the thing measured. (A block average divided by 2 instead of 20 produced exactly such a number during these experiments and was caught this way.)
  • Do not measure tiny jobs. Prefill speed on a 16-token prompt varied from 90 to 317 tok/s between identical runs: the job is a few milliseconds and fixed overhead swamps it. Prefill is measured in Chapter 6 with prompts long enough to mean something.

  • Profile by cutting at the boundary between the forward pass and everything around it.

Appendix C

Tooling notes

Small things that stop beginners once and should not stop them twice.

MLX is lazy

Writing mx.sum(x) does no work. MLX records an IOU and moves on; the work happens when something needs the answer. mx.eval(...) means "do the work now". Any timing without it measures the writing of an IOU, which takes no time. The pattern is always: start the clock, mx.eval(the thing), stop the clock. A call to .item(), which converts a one-element array to a Python number, also forces evaluation.

Warm up, then repeat

The first run of anything on the GPU includes one-time setup: compiling the small program, allocating memory. Do one untimed run before the clock starts, then average several timed runs.

The batch dimension

Models expect a batch of sequences even when there is one. mx.array(ids)[None] adds that outer dimension; the logits come back as (batch, positions, vocabulary).

Running a file versus the interactive prompt

.venv/bin/python alone opens Python's interactive mode, with a >>> prompt waiting for code. Type exit() to leave. To run a file, put its path after the interpreter.

Reading an f-string

In f"read {nbytes / 1e9:.1f} GB", the f means "fill in the braces", the braces hold a calculation, and :.1f after the colon means one digit after the decimal point. :3d is a whole number padded to three characters. 1e9 is one billion.

Indentation is structure

Everything indented under a for runs every iteration. A summary loop that should run once must start at the left margin, or it prints every step.

Array dimensions are limited to 2³¹ elements

A one-dimensional array of four billion numbers overflows a 32-bit index. Give the array two dimensions, such as (4000, 1_000_000); mx.sum still adds every element.

Appendix D

Glossary

Activations
The temporary values computed for one input as it flows through the layers. Created and discarded every token, unlike the weights.
Argmax
The index of the largest value. Applied to logits, the greedy choice of next token.
Autoregressive decoding
Producing a sequence one token at a time, each new token depending on all previous ones. Each token costs one full forward pass over the weights.
Bandwidth
Bytes per second between memory and processor. Bus width × transfer rate for the spec; measured by timing a large read.
bf16
A 16-bit (2-byte) floating-point format, the usual "full precision" for inference weights.
Ceiling / roofline
The best possible speed given a hardware limit. For decoding: measured bandwidth ÷ bytes of weights.
Decode
The phase that produces the answer, one token per forward pass. Memory-bound.
Fixed overhead
The cost of launching any GPU operation regardless of its size, about half a millisecond on the reference machine. Dominates small jobs.
Forward pass
One trip of input through all the model's layers to produce logits.
KV cache
The model's stored memory of earlier tokens, so each new token does not reprocess the conversation. Chapter 6.
lm_head
The final matrix that turns a hidden vector into one logit per vocabulary entry. About a tenth of Qwen3-4B's weights.
Logits
The raw scores, one per vocabulary entry, that the model outputs for the next token.
Memory-bound
Limited by how fast bytes move rather than how fast arithmetic runs. Decoding is memory-bound.
Prefill
The phase that processes the prompt, all tokens at once. Compute-bound. Chapter 6.
Quantization
Storing weights in fewer bits, for example 4 instead of 16, to shrink the book.
Softmax

Guessing several tokens cheaply and verifying them all in one pass of the large model, so one read yields several tokens.
tok/s and TPOT
Tokens per second and its inverse, time per output token. The primary decode metric; report it warmed up, sustained, with the prompt phase excluded.
